# kusanagi

两台机器上的两个 agent 要说话。你不想自己跑一台服务器，也不想让保管消息的那台主机知道谁在跟谁联系。

kusanagi 是一个命令行程序，专门做这件事。消息是加密的，而且保管消息的主机分不出哪些消息属于同一场对话，也看不出是谁写的。

```bash
# 在 Alice 的机器上
kusanagi invite --name bob --waypoint http://box.example:8443
# 输出：kusanagi1:0100cff7...

# 在 Bob 的机器上——用管道递进去，不作为参数粘贴
pbpaste | kusanagi join --name alice
kusanagi send --to alice "构建通过了"
```

配置到此为止。没有账户，没有配置文件，也不需要你自己的服务器。

**版本 0.0.1，pre-alpha。密码学部分没有经过任何外部审计。线格式会变，且不提供迁移路径。**

## 安装

```bash
git clone https://github.com/2youg1/kusanagi
cd kusanagi
cargo build --release      # 产物是 target/release/kusanagi
```

需要 Rust 1.97 或更高版本。没有别的依赖，不需要 C 工具链，也没有运行时。

## 五分钟上手

跑 `just demo` 可以在一个临时目录里看到下面整个过程。也可以手动来一遍。

**1. Alice 开一条 channel。** 她指定一个存放消息的地方，拿到一行文本交给对方。

```bash
kusanagi --root ~/.alice invite --name bob --waypoint http://box.example:8443
```

**2. Bob 加入。** 他只需要这一行，别的都不需要。

```bash
pbpaste | kusanagi --root ~/.bob join --name alice
# 或：  kusanagi --root ~/.bob join --name alice < invitation.txt
```

**邀请从标准输入读取，不能作为参数传入。** 它携带着通道秘密，而在 Linux 上本机任何一个账号都能从 `/proc` 读到别的进程的命令行，shell 还会把它写进历史记录。把这行字当密码对待，就意味着永远不让它变成一个参数。

这行邀请只能用一次。如果别人先用掉了，Bob 会收到 `kusanagi.invite_spent`，这时应该去要一条新的，而不是重试。

**3. 两边开始说话。**

```bash
kusanagi --root ~/.alice send --to bob "alice 说的第一句话"
kusanagi --root ~/.bob   read --from alice
kusanagi --root ~/.bob   send --to alice "bob 听到了"
kusanagi --root ~/.alice read --from bob
```

每次读取都会把整条链验一遍：每条消息都要对上作者的签名，也要对上它前面那一条。任何一项对不上，你拿到的是错误而不是列表。这里没有「读一半」这种结果。

**4. Alice 反悔了。**

```bash
kusanagi --root ~/.alice revoke --from bob
```

此后 Bob 写的东西一律不被接受，包括他在此之前写的。Bob 不会收到通知，因为已经没有信道可以通知他了：他那边继续显示授权有效，而 Alice 的 `channels` 显示他已被切断。

如果 Alice 想彻底丢掉这条 channel，用 `kusanagi forget --channel bob`。主机上的字节原样保留，但这条 channel 再也进不去了。

`docs/joining.md` 用一页纸讲同一件事，写给完全没见过这个仓库的人。

## 命令

| 命令 | 作用 |
|---|---|
| `id` | 显示本端点的 handle。首次使用时生成身份。 |
| `invite --name N --waypoint W [--for SECS] [--can send,read]` | 开一条 channel，签发一条邀请。 |
| `join --name N` | 接受一条邀请，从标准输入读取。它永远不是参数，理由见第 2 步。 |
| `send --to N ["文本"]` | 追加一条消息。不给文本时，内容从标准输入读取。 |
| `read --from N [--after H] [--mine]` | 读取对方的消息，从头验证。`--after H` 只返回高度 `H` 之后的部分，`--mine` 读你自己的。 |
| `channels` | 列出本机的 channel，各自还允许什么，以及到什么时候为止。 |
| `revoke --from N` | 切断一个对端，立即且永久。 |
| `forget --channel N` | 在本端点丢弃一条 channel。 |
| `doctor <WAYPOINT>` | 实测一台主机的真实行为，并出具证书。 |
| `host --bind ADDR --dir PATH` | 让本机充当别人的存放主机。 |

所有命令都接受 `--json`。所有失败都带一个稳定的错误码，以及一条能让你走出去的命令——参数打错也算一种失败，同样有。

## 在程序里调用

这是 agent 使用 kusanagi 的正规方式。有四点值得知道。

**用管道传内容，不要拼进命令行。** 不给文本参数时内容从标准输入读取，引号、换行以及根本不是文本的数据都能原样送达。

```bash
jq -c '{task: "review", pull: 42}' < job.json | kusanagi send --to alice
```

**解析 `payload`，不要解析 `text`。** `payload` 是小写十六进制的原始字节，无损。旁边的 `text` 是给人看的，遇到非 UTF-8 的内容会静默替换字符。

**轮询用 `--after H`。** 一次请求同时回答两个问题：有没有新的，以及新的是什么。无论有没有返回消息，`height` 给出的都是已验证的链头。

```bash
kusanagi --json read --from alice --after 6
```

**用 `--mine` 找回自己的位置。** 循环中途被杀掉的 agent 可以用它读回自己的高度，不必靠写一条消息来试探。

无论对话已经进行了多久，一次轮询只向主机发一个请求。这是隐私性质而不只是速度问题，理由见[主机能看到什么](#主机能看到什么)。

## 消息存在哪里

```text
/var/lib/kusanagi                    本机上的一个目录
http://box.example:8443              某人在跑 `kusanagi host`
s3://ACCOUNT.r2.cloudflarestorage.com/bucket?region=auto
```

对象存储从 `KUSANAGI_S3_ACCESS_KEY` 和 `KUSANAGI_S3_SECRET_KEY` 读取凭据。

**信任一台主机之前，先用 `kusanagi doctor` 测它。** 各家 S3 兼容存储对条件写的支持并不一致，而且不一致的方向很危险：条件被忽略、写入照样成功，于是「一个地址写过就不能被覆盖」这个前提悄悄失效。`doctor` 会写两次再读回来，告诉你这台主机够得上哪一档。

## 主机能看到什么

主机是不被信任的，也不需要被信任。它究竟能知道什么，列在下面。

| | 状态 |
|---|---|
| 消息内容 | **看不到。** ChaCha20-Poly1305，每条消息一把只用一次的密钥。 |
| 消息是谁写的 | **看不到。** 作者在密文里面，不在旁边。 |
| 哪些消息属于同一场对话——从它**存下来的东西**看 | **看不到。** 每个地址都是 `KDF(共享秘密 ‖ 作者 ‖ 高度)`，地址从不重复使用。 |
| 哪些消息属于同一场对话——从它**被请求的东西**看 | **轮询时看不到。** 一次轮询只点名一个地址。详见下文。 |
| 一共存了多少个对象 | **看得到。** |
| 每个对象多大 | **看得到**，精确到字节。 |
| 每次请求什么时候到达 | **看得到。** |

第四行以前是破的，修好没多久。读取方过去每次都从高度零开始走，于是把这场对话的全部地址按顺序、在同一个连接上、一口气报给了主机。地址本身推导得再无关，读取顺序还是把分组关系直接交了出去。主机不需要做任何密码分析，一份访问日志就够了。

现在端点会记下每条流验证到哪里，于是一次轮询只问一个地址就停。有两件事这个修法并没有解决：

- 第一次追赶一条从没读过的流时，取到哪一层就会点名哪一层。
- 长期盯着某一个端点看的主机，可以跟着「活动边缘」走：一次命中之后被轮询的那个地址，就是同一条流的下一条。要堵住这个需要长轮询，它在[还没做的部分](#还没做的部分)里。

**有两件事主机做不到。**

*它没法给你投递任何你没要求过的东西。* 要写给你就得知道你的地址，要推导你的地址就得有共享秘密，要拿到秘密就必须被正式引荐过。垃圾消息在这里不是被过滤掉的，而是算不出来。

*它没法把你往回拉。* 主机可以拒绝提供某条消息，这个谁也拦不住。但只要你已经读到某个高度，它再删掉或替换比这更早的内容，得到的是 `kusanagi.history_changed` 这个错误，而不是被当成一场更短的对话默默接受。「她根本没发过那条撤回」——这种谎，保管消息的人说不了。

上面这些不是宣称，是测出来的。`crates/kusanagi/tests/unlinkable.rs` 站在主机一侧，检查一百条消息；`unwatched.rs` 站在一台记访问日志的主机一侧；`lying.rs` 站在一台会删除和搬移对象的主机一侧。`adversary/` 是一个独立的 Haskell 程序，用你会用的方式驱动这个二进制去找反例——上面那个「往回拉」的漏洞就是它找出来的。

## 工作原理

每个地址是 `KDF(共享秘密 ‖ 作者 ‖ 高度)`。在主机眼里，同一场对话里的两条消息就是两串互不相干的 160 位随机数。

每个地址各自推导出自己的密钥，所以每条消息用的密钥都只用这一次。

被加密的是整条消息，作者也在里面。如果只加密正文，主机就能按作者把消息归堆。

消息带签名并且用哈希前后串起来，读取方不需要问任何人就能确认作者和顺序。

权限是一条由签名委托组成的链，只能收窄。它离线可验，撤销其中一环，其下的全部随之失效。

本地保存的东西只有三样：一颗身份种子、每条 channel 一个文件，以及每条流验证到哪里的记录。三样里只有最后一样可以重算，删掉它只改变读取的开销，不改变读取的结果。

`ARCHITECTURE.md` 是详细版本，包含每个选择背后的理由，以及那些被否决的方案。

## 还没做的部分

列在这里，是为了让每一处缺失都是一个决定，而不是一次疏忽。

| 缺什么 | 为什么 |
|---|---|
| 一条 channel 容纳三方以上 | 一条 channel 就是一对端点。多方需要成员名册，而名册正是这套设计要藏起来的关系图。 |
| 隐藏你发了多少、什么时候发 | 填充和抖动没有真实审查者可以对着失败，无法验证。 |
| 对哑对象存储隐藏对象数量 | 需要长轮询，而普通桶不提供。 |
| 长轮询 | 顺带能堵住上面说的活动边缘泄露。 |
| 分块的共享工作区 | 另一个问题。目前单条消息上限 64 KiB。 |
| MCP 前端 | 动词集合是一个枚举，第二个前端是纯增量工作。 |
| 后量子套件 | 等经典套件定下来之后干净地加上去。 |
| 安全审计 | **没做。** 这个仓库之外没有任何人审过这里的密码学。 |

## 参与开发

```bash
just check        # fmt、clippy（-D warnings）、测试、行数预算、cargo-deny
just demo         # 在一个用完即删的目录里跑通整个故事
just adversary    # Haskell 反例猎手，装了 GHC 才跑
```

`just check` 是每一次改动的收工条件。它会跑 177 个测试，其中包括两个端点通过真实 TCP 对话。

动第一行代码之前先读 `AGENTS.md`。每个 crate 都有一份 `<crate>-SPEC.md`，它先于代码改动。

`adversary/` 在 Cargo workspace 之外、发布物之外、`just check` 之外，所以你改这里的任何东西都不需要装 GHC。它通过 `--json` 驱动已发布的二进制，寻找违反承诺的轨迹，并把找到的东西作为一个 Rust 测试提交到 Rust 代码旁边。

## 相关项目

[sprawling-agents](https://github.com/2youg1/sprawling-agents) 是同一个问题的另一半。kusanagi 让一对端点拥有一段别人读不到、关联不了、也排不出序的历史；sprawling-agents 让同一台机器上的一群 agent 共用一条只增不减的账本。因为在一台机器内部，真正有用的问题是「谁在先」，而只有全序能回答它。可一旦跨机器，同样的全序就成了旁观者能读到的事实——这正是这里的地址靠推导而不靠协商的原因。
